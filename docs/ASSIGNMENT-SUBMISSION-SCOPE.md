# 학생 과제 제출 기능 — G1 범위와 동작 규칙

## 목표

HRA 사이트를 간단한 학사관리 시스템으로 확장할 때, 첫 번째 기능은 **학생이 과제를 제출하고 운영진이 학생별 제출 여부를 확인하는 것**이다. 대학교 학사시스템의 모든 기능을 한 번에 도입하지 않는다.

이 문서는 기능 범위와 #140·#141에서 확정한 G1 운영 규칙을 기록한다. **2026-10-16 기준, #144~#158의 명부·과제·개인 제출·비공개 파일·학생/승인자 화면 코드와 격리 검증이 구현됐다.** 학사 공개·쓰기·업로드·정리 설정의 기본값은 비활성이며, 코드 구현은 운영 출시를 의미하지 않는다. 실제 운영 설정은 별도로 확인한다. 개인정보 보존·파기·백업(#142), 교수 검토·출결·수료(#143) 정책은 미정이고, 관측·통합 CI(#157·#158) 코드와 격리 검증도 포함한다.

## 이 문서를 읽는 방법

화면·서버 기능을 구현하거나 검수하는 개발자를 위한 문서다. 먼저 “G1 최소 사용 흐름”과 확정 규칙 표로 정상 동작을 확인하고, 뒤의 오류 시나리오와 수용 테스트로 실패할 때의 결과를 확인한다. 업로드 성공, 서버의 파일 검증, 최종 제출 확정은 서로 다른 단계다.

업무 범위는 [학사 로드맵](ACADEMIC-MANAGEMENT-ROADMAP.md), DB 관계는 [데이터 모델](ACADEMIC-DATA-MODEL.md), 낯선 용어는 [용어집](getting-started/glossary.md)을 참고한다. 이 문서의 화면·서버 경로는 현재 구현을, G2/G3와 정책 미정 항목은 후속 작업을 뜻한다.

## 확정된 방향

- 과제 업로드의 주체는 **학생**이다. 학생이 자신의 결과물을 제출한다.
- 제출 내역은 학생 개인과 연결되어야 한다. 운영진은 과제별로 누가 제출했는지 확인할 수 있어야 한다.
- 기존 `주차별 텍스트`와 `수업일지`는 기수에 공유하는 자료이므로, 학생별 과제 제출 내역으로 간주하지 않는다.
- 첫 단계는 과제 제출에 집중한다. 성적, 출석, 휴학·복학·수료 등 학적 상태 관리는 이번 범위에 넣지 않는다.

## 공동 자료와 개인 과제의 차이

| 현재 기능 | 확인된 상태 | 과제 제출에 필요한 차이 |
|---|---|---|
| 회원·기수 | `users.role`, `users.cohortId`로 접근 권한과 현재 기수를 관리한다. | 학생이 자기 기수의 과제와 **자기 제출 내역**만 볼 수 있어야 한다. |
| 주차별 텍스트 | 회원이 기수별 자료를 업로드한다. `weeklyTexts`에는 제출 학생이나 과제와의 연결이 없다. | 학생별 제출 기록을 별도로 저장해야 한다. |
| 수업일지 | 작성자 `authorId`를 기록하지만 기수에 공유하는 수업 기록이다. | 과제·제출 상태·제출 파일을 연결하는 별도 흐름이 필요하다. |
| 일정 | 수업 설명에 과제를 적을 수 있다. | 설명 문구만으로는 학생별 제출 여부를 집계할 수 없다. |

위 표는 기존 공동 자료와 개인 제출을 구분하기 위한 차이다. 개인 과제에는 별도로 구현된 `academic_students`, `cohort_enrollments`, `assignments`, `assignment_targets`, 최종 제출·파일·업로드 의도를 사용한다. 서버 계약은 [학생 조회](developer/academic-student-queries.md), [과제 관리](developer/academic-assignment-actions.md), [비공개 업로드](developer/academic-assignment-uploads.md), [최종 제출](developer/academic-submission-finalization.md), [파일 다운로드](developer/academic-submission-files.md)를 따른다.

관련 코드: `src/lib/db/schema.ts`, `src/features/academics/`, `src/features/weekly-texts/actions/index.ts`, `src/features/class-logs/actions/index.ts`.

## G1 최소 사용 흐름

아래 흐름의 G1 코드는 구현됐다. 과제 등록·공개와 전체 제출 현황·파일 조회는 홈페이지 관리자 역할만으로 허용하지 않고 지정된 학사 승인자의 검증된 계정 ID로 인가한다. 실제 운영 사용은 #142 정책과 운영 활성화 절차를 충족한 뒤 가능하다.

1. 운영진이 과제의 제목, 안내, 대상 기수, 마감일을 등록한다.
2. 해당 기수의 학생은 `내 과제`에서 과제와 마감일을 확인한다.
3. 학생은 파일을 제출하고 자신의 제출 시각·파일·제출 상태를 확인한다.
4. 운영진은 과제별 대상 학생 목록에서 미제출·제출 여부를 확인하고 제출 파일을 열람한다.

최소 데이터 단위는 **과제**, **학생**, **학생의 과제 제출 기록**이다. 파일 자체와 제출 기록을 분리해, 파일이 누구의 어떤 과제 제출물인지 추적할 수 있어야 한다.

## G1 동작의 완료 기준

- 다른 기수 학생에게는 대상 과제가 보이지 않고 제출할 수도 없다.
- 학생은 다른 학생의 제출 내역이나 파일을 볼 수 없다.
- 운영진은 과제별 대상 학생의 제출 여부를 확인할 수 있다. 제출이 없는 학생도 목록에 나타난다.
- 업로드 실패 시 제출 완료로 표시되지 않는다. 제출 성공 시 학생 화면과 운영진 화면에 같은 결과가 보인다.
- 제출 파일은 URL을 아는 것만으로 열리지 않도록 접근 권한을 확인한다. 기존 자료실의 공개 Blob URL 방식을 학생 제출물에 그대로 적용하지 않는다.

## 이번 범위에서 제외

성적·평가, 피드백, 재제출 이력, 출석, 학적 상태 변경, 학생별 성적표, 알림은 첫 버전의 필수 기능으로 잡지 않는다. 필요해지면 별도 범위로 정의한다.

**후속 출결 운영의 확인된 사실:** 교수는 출결 담당자가 아니다. HRA 수업에는 **어드바이저(Advisor)**라는 별도 운영자가 있다. 출결은 G2에서 어드바이저·조교의 기수별 기간 배정과 권한을 기반으로 추가한다. 어드바이저 1명과 조교 2명이 돌아가며 출결을 확인하며, 조교 교체 이력을 보존한다. 과제 평가를 담당할 수 있는 교수진과 출결을 운영하는 Advisor는 별개다. 세부 배정·정정·승인 규칙은 [#143](https://github.com/Human-Renaissance-Academy/hra-website/issues/143), 업무 권한 구현은 [#165](https://github.com/Human-Renaissance-Academy/hra-website/issues/165)로 추적한다. 이 사실이 G1 과제 제출 MVP의 범위를 확장하지는 않는다.

## G1 확정 운영 규칙 (#140·#141)

| 항목 | 확정 규칙 |
| --- | --- |
| 대상 학생 | 운영 책임자가 확인·승인한 기수별 학적 명부. 지원서 합격, 사이트 회원 역할·기수, 이메일 일치만으로 자동 등록하지 않음 |
| 대상 확정 | 과제 **최초 공개 시** 해당 기수의 유효한 등록 학생 전체를 스냅샷으로 저장. 이후 명부 변경으로 과거 대상·분모를 자동 수정하지 않음 |
| 마감 | 초안에는 마감 시각이 없어도 되지만 **공개에는 미래의 마감 시각이 필수**. `Asia/Seoul` 입력을 UTC 시각으로 저장하고 서버 시각으로 판정 |
| 마감 후 | 최종 제출 확정 시각이 마감 시각 이상이면 차단. 지각 제출 상태는 G1에 없음 |
| 재제출 | 최종 제출은 학생·과제 대상당 1건. 완료 후 교체·재제출 불가; 응답 유실에 따른 같은 요청의 멱등 재조회만 허용 |
| 파일 | 비어 있지 않은 PDF 정확히 1개, **50MiB(52,428,800바이트) 이하**. `.pdf` 확장자·`application/pdf` MIME·PDF 시그니처를 함께 검증. 다른 형식·추가 파일 거부 |
| 열람 | 학생은 본인 것만, G1 운영 승인을 받은 담당자만 대상 전체 현황·파일 열람. 교수·어드바이저는 역할 또는 배정만으로 개인 제출물 열람 불가 |

관리 최종 승인자는 이번 정책을 승인한 HRA 운영 책임자 본인이다. 구현에서는 검증된 로그인 계정 ID로 승인자를 지정하며 홈페이지 `ADMIN` 역할만으로 학사 승인 권한을 추정하지 않는다. 명부·계정 연결의 증빙과 거부·재처리는 [학사 데이터 모델](ACADEMIC-DATA-MODEL.md)에 기록한다. 보존 기간·파기 절차는 #142에서 별도로 확정한다.

| 명부·과제 상황 | 과거 과제 대상 및 미제출 분모 |
| --- | --- |
| 과제 공개 전 학생 신규 등록 또는 등록 취소 | 공개 시점의 유효 명부만 스냅샷에 포함 |
| 과제 공개 후 학생 신규 등록 | 기존 과제에는 자동 추가하지 않음. 새 학생에게 필요한 과제는 별도 공개 과제로 처리 |
| 공개 후 중도 탈퇴 또는 계정 해제 | 과거 대상 행을 보존하고 제출 기록을 삭제하지 않음. 최종 제출이 없다면 미제출로 표시하며 탈퇴 사실은 별도 상태로 구분 |
| 공개 요청 재시도·재공개 | 기존 스냅샷을 다시 사용하고 대상 행을 중복 생성하지 않음 |

G1에서는 공개 후 대상 추가·제외를 허용하지 않는다. 예외가 필요하면 분모·감사 이력·보존 정책을 별도 이슈에서 결정한 뒤 구현한다.

| DB의 최종 제출 판정 시점·상황 | 결과 |
| --- | --- |
| 마감 시각 없음 | 초안 저장 가능, 과제 공개는 입력 오류로 거부; 학생에게 제출 경로 노출 안 함 |
| DB가 제출 시각을 정하고 재검사할 때 마감 1초 전 | 대상·파일 등 다른 검증도 통과하면 최종 제출 1건 확정 |
| DB 판정 시 마감 정각 또는 1초 후 | 최종 제출 거부, 제출 행 없음. 지각으로 저장하지 않음 |
| 마감 전 업로드, 마감 이후 최종화 | 업로드만으로 제출 완료가 아니므로 최종화 거부; 미확정 파일은 정리 대상 |
| 마감 전 확정 후 동일 키 재시도 | 마감 이후에도 기존 성공 결과를 반환. 멱등 조회를 마감 판정보다 먼저 수행하고 새 파일이나 새 제출을 만들지 않음 |

요청을 마감 전에 시작했더라도 검증·DB 잠금 대기 중 마감을 넘으면 실패할 수 있다. 서버 액션의 실패 결과 객체에 포함된 `status: 409` 같은 값은 앱의 오류 계약이며, 브라우저가 받은 HTTP 응답 상태와 동일하다고 가정하지 않는다. 과제 관리 액션은 `success`, `message`, `referenceId`로 결과를 전달한다.

**수용 테스트:** 최초 공개 대상 N명과 미제출 분모 N명 일치, 신규 등록·탈퇴 후 기존 분모 불변, 동시 공개 재시도 시 대상 중복 0건, 마감 1초 전/정각/1초 후 서버 시각 판정, 마감 이후 최종화 거부, 동일 키 재시도 멱등성, 최종 제출 뒤 다른 키·다른 파일의 재제출 거부, PDF 크기·확장자·MIME·시그니처 경계 및 추가 파일 거부를 검증한다.

**후속 결정:** 보존·파기 기간(#142), 교수의 담당 과제 검토 범위와 출결 운영(#143)은 G1 규칙으로 확정하지 않았다.

## 1차 MVP 상세 실행 계약 (2026-10-13 보강)

이하 내용은 확정된 G1 운영 규칙을 구현하기 위한 설계·수용 기준이다. 보존과 G2/G3의 운영 정책은 아직 미정이다.
전체 순서와 후속 G2/G3는 [학사관리 전환 로드맵](ACADEMIC-MANAGEMENT-ROADMAP.md), 신규 테이블·DB 제약·마이그레이션은 [학사 데이터 모델](ACADEMIC-DATA-MODEL.md)을 따른다.

### 1. 기수별 등록 학생과 제출 대상

- G1에서는 과제 제출에 필요한 최소 학생 식별·기수 등록(`academic_students`, `cohort_enrollments`)만 도입한다. **학적 상태 전환/휴학/수료 판정은 G1 범위가 아니다.**
- 로그인 계정과 학적은 별도다. 운영진이 확인하지 않은 지원서/이메일 일치만으로 학적을 자동 연결하거나 `MEMBER`로 승격시키지 않는다.
- 과제 최초 공개 시 해당 기수의 **검증·승인된 등록 학생 전체**를 `assignment_targets`로 확정한다. G1에서 공개 후 대상 변경은 허용하지 않는다.
- 운영진의 미제출 명단은 `대상 학생 LEFT JOIN 최종 제출`을 기준으로 한다. 학생이 과제를 한 번도 열지 않아도 미제출 명단에서 누락되지 않는다.
- 학생의 공개 자료 `weekly_texts`/수업일지 `class_logs` 업로드 성공을 이 과제의 제출로 계산하지 않는다.

### 2. 과제 등록·공개 (운영진)

| 입력 | G1 계약 | 서버 검증 |
| --- | --- | --- |
| 대상 기수 | 기존 `cohorts.id` 한 개 | 존재·상태·관리 권한 확인 |
| 과제 제목 | 필수 | 공백 제거·길이 상한 |
| 과제 안내 | 일반 텍스트, 선택 | 길이 상한·React 텍스트 렌더링, 줄바꿈 보존 |
| 수업 연결 | 기존 `schedule_events.id` 선택 | 해당 수업의 기수 일치 검사 |
| 마감 시각 | 초안은 선택, 공개 시 미래 시각 필수 | `Asia/Seoul` 해석·UTC 저장·서버 시각 비교 |
| 공개 상태 | `DRAFT` → `PUBLISHED` | 공개 시 대상 학생 확정, 재공개 멱등성 |

- 다른 기수나 비공개 과제의 URL을 직접 호출해도 조회·제출할 수 없어야 한다.
- 현재 G1은 제출자 유무와 관계없이 **공개 이후** 과제 정의의 수정·삭제와 대상 변경을 거부한다. 공개된 과제는 허용된 종료 절차를 사용하며, 보존·파기 정책을 임의의 삭제로 대체하지 않는다.

### 3. 학생의 제출 흐름

1. 서버에서 로그인, `MEMBER` 권한, 검증된 `academic_students.user_id`, 해당 과제의 `assignment_targets` 포함 여부를 확인한다.
2. 학생의 UI에는 공개된 자기 기수의 과제와 마감·상태만 표시한다. 타 학생 이름·제출 파일·관리자 내부 상태를 내려주지 않는다.
3. 서버에서 파일 형식·개수·크기·업로드 대상/만료시간을 검증한 뒤 임시 업로드 의도를 발급한다. 클라이언트가 제출한 임의 파일 URL로 최종 저장하지 않는다.
4. 업로드 성공 후 저장 객체와 의도의 매칭을 재검증하여 최종 제출을 확정한다. **파일 업로드 성공만으로 제출 완료 UI를 띄우지 않는다.**
5. 제출 확정은 `submission_key`로 멱등하게 처리한다. 응답이 유실되면 재조회/재시도로 기존 제출 결과가 복구되어야 한다.
6. 학생은 최종 제출 시각·파일명·상태를 확인한다. 파일 열람은 매 요청별 서버 접근 검증을 거친다.

### 5. 권한·보안·프라이버시

- G1은 **계정 ID로 지정된 운영 책임자의 과제 관리/제출 확인**과 **해당 학생 본인 제출**에 집중한다. 홈페이지 `ADMIN` 역할만으로 학사 권한을 부여하거나 FACULTY 전체에 학생 제출물을 노출하지 않는다.
- Advisor는 수업 운영/출결 담당이며 이 사실만으로 **학생 개인 과제 파일이나 전체 학적에 접근하는 권한을 부여하지 않는다.** 출결 기록·정정 권한도 G1에는 구현하지 않는다. FACULTY에게 출결 권한을 부여하지 않는다.
- 제출 파일은 공개 Blob이 아니라 비공개 저장소 및 인증된 파일 전달 경로로 처리한다. 권한 검사는 UI뿐 아니라 업로드 승인, 최종화, 상세 조회, 파일 다운로드에서 모두 반복한다.
- 서버가 학생 ID, 기수 ID, 파일 소유자, 제출자 정보를 인증 세션·DB 기준으로 결정한다.
- 마감·파일 형식·재제출 정책은 위 G1 규칙을 따른다. 파일 보존·삭제와 개인정보 파기 기간(#142), 교수진 검토 범위(#143)는 **미확정**으로 유지한다.
- 감사 로그에는 actor, resource ID, action, 시각, 결과, 요청 상관 ID를 남기되 이메일·답변 원문·파일 URL·인증 비밀값을 기록하지 않는다.

### 7. G1 통합/E2E 수용 테스트 (필수)

아래는 전체 수용 기준이며 자동으로 완료 처리하지 않는다. 구현 단위의 격리 PostgreSQL·실제 HTTP/브라우저 검증과 [G1 전용 통합 CI](developer/academic-g1-quality-gate.md), 운영 DB·저장소 적용 및 백업/복원 확인을 구분한다. 코드·로컬 검증 통과만으로 운영 출시를 선언하지 않는다.

- [ ] 기수 A 학생, 기수 B 학생, `PENDING`, 비로그인, `FACULTY`, `ADMIN` 조합으로 목록·상세·서버 액션·파일 API 권한 검사
- [ ] 해당 기수에 등록돼 있으나 미제출인 학생이 관리자 명단에 표시되고 제출 후 즉시 카운트가 일치
- [ ] 동일 사용자의 같은 기수 이중 등록·같은 과제 이중 제출 및 두 요청 동시 제출 차단
- [ ] 파일 업로드 직후 취소, 업로드 실패, 최종 DB 기록 실패, 성공 응답 유실을 주입해 부분 데이터/중복 없는지 검증
- [ ] 비공개 파일 URL/타 학생 파일 ID 직접 접근 차단; 서버 로그에 파일/PII 유출 없음
- [ ] 학생이 타 기수·비공개·마감 과제에 직접 제출을 시도할 때 서버 정책이 적용되는지 검증
- [ ] 기수 삭제·계정 삭제·과제 비공개 전환 시 보존 대상 기록이 연쇄 삭제되지 않는지 확인
- [ ] KST 마감 1초 전/정각/1초 후 경계 테스트(정각부터 제출 거부)
- [ ] 신규 마이그레이션 dry-run·반복 실행·rollback 또는 복구 절차가 격리된 테스트 DB에서 검증됨
- [ ] Playwright 핵심 G1 플로우가 CI에서 실행되고 실서비스 DB·Blob에 쓰기 요청하지 않음

### 8. 기존 이슈와의 경계

기존 보안·무결성·파일 제한과의 중복 구현을 막는다. 권한 기반은 #89·#123, 기존 Blob 정책은 #88·#101, 업로드 한계는 #102·#110, 제출 원자성 참고 사례는 #97, CI 기반은 #103, 기수 삭제 정책은 #109, 기존 모집 접수 정책은 #104를 먼저 확인한다.

G1 새 과제의 비공개 업로드/다운로드는 **기존 공개 자료실 업로드 변경과 별도의 과제 도메인**으로 구현하되, 공통화가 안전하다고 검증된 최소 코드만 재사용한다.
